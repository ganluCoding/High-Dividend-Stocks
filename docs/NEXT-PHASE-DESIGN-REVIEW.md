# 下一阶段设计审阅报告

- 审阅对象：[NEXT-PHASE-DESIGN.md](NEXT-PHASE-DESIGN.md)
- 日期：2026-08-09
- 审阅角色：资深中国高股息投资顾问、桌面数据产品/软件架构专家、桌面端 UX 审阅者
- 结论：**有条件通过；先完成 P0 修订，再进入规则引擎或桌面端开发。**

## 一、总体结论

三位审阅者一致认可以下方向：股票与 ETF 分开、周期股单列、桌面端不自动下单、事实数据与个人判断隔离、前台不展示全市场噪音。

阻断开发的问题也高度一致：当前设计仍可能把“已发布日终参考价、有限低频覆盖、历史 TTM 现金分配”呈现得过于像“全市场、实时、可执行的推荐”；同时，现有运行时库是持续写入的活库，尚不能以 `release_id` 真正重放旧研究结论。

## 二、P0：开发前必须修订

### P0-1：发布版本必须成为不可变发布包

**问题**：当前 `database_releases` 指向持续更新的运行时数据库路径；仅保存 `release_id` 和哈希，不能保证未来可打开或重算当时的事实。日行情和低频任务也会写同一活库。

**风险**：历史草案点开时可能读到今天的数据；每日和每周任务可能形成混合时点；“可复现”变成仅能展示旧结果，不能验证。

**必须修订**：定义发布包并引入唯一发布锁。

```text
releases/<release_id>/
  facts.sqlite             # 完整、只读、不可再写的事实快照
  manifest.json            # 各数据集watermark、覆盖率、QC、schema、父版本
  manifest.sha256
  raw-inputs.json          # 原始run与hash引用

current-release.json       # 原子切换的当前发布指针
```

所有采集任务只写暂存区；只有发布器取得 `publisher.lock` 后才能构建发布包。保存筛选、草案或导出时，必须传入明确 `release_id`；`latest` 只能用于首页浏览。

### P0-2：把低频覆盖和 PIT 变成机器可判定的字段合同

**问题**：设计承认只有 31 只股票和 5 只 ETF 完成低频事实，但“完整”“新鲜”“连续分红”等硬门槛仍只是名称。分红、财报的公告时间、修订和实施状态也未定义为筛选语义。

**风险**：有一项数据就可能被误判完整；后来披露的财报可能回填旧时点；有限覆盖被包装为全市场初筛。

**必须修订**：先建立 `CoverageMatrix` 与 PIT 字段目录。

```text
instrument_id + dataset + required_history_window
+ latest_effective_date + latest_available_date
+ collection_status + verification_status
+ completeness_ratio + freshness_status + source_tier
```

每个规则模板声明自己的 `DataRequirements`。任何用于规则的字段至少包含：`report_period_end`、`published_at`、`effective_at`、`observed_at`、`source_version`。缺失公告日期或未完成核验时，状态只能是“资料不足”。

### P0-3：锁定股票、ETF 与周期股的收益率口径

**问题**：设计使用“TTM 已实施现金收益率”，但没有锁定特别分红、除权日、拆分/送转、税前税后和分母价格日期；ETF 实际分配率与股票股息率在前台仍可能被横向比较。

**风险**：一次性特别分红被理解为长期收益；ETF 分配被理解为企业股息或基金总回报；同一公司不同运行时得到不可复核的数字。

**必须修订**：字段目录至少固化：

```text
ttm_cash_dividend_yield_gross =
过去12个月、在cutoff前已实施且公告已核验的税前每股现金股利（复权调整后）
÷ 该release对应的已发布收盘价
```

- 常规与特别分红必须分列；特别分红默认不进入“稳健分红”核心规则。
- ETF 前台字段改为“过去12个月现金分配率（非股息率、非总回报）”。
- 股票与 ETF 独立列表、独立排序、独立风险说明。
- 周期股不得进入稳健分红模板；需要 `normalised_dividend_capacity`，数据不足只能观察，且未设周期上限时不得进入组合草案。

### P0-4：重定义前台状态、参考价和草案导出门禁

**问题**：事实库目前是日终快照，设计却使用“当前价”；`eligible`、`入选`容易被理解为推荐；草案按历史收盘价取整后没有失效机制。

**风险**：用户把日终价格当实时下单价；隔夜价格变化后仍导出错误数量；“资料完整”被理解为“值得买”。

**必须修订**：

- 前台统一使用“已发布收盘价（日期）/参考价”，禁止称“当前价”。
- `eligible` 前台改为“资料足以研究”；固定提示“符合研究规则不代表估值合理、未来分红可持续或适合买入”。
- 草案保存 `reference_price`、`price_as_of`、`lot_size`、费用假设和约束结果；超过一个交易日或券商价格偏离参考价阈值时标记“需重算”。
- 未有健康发布版本、价格超过新鲜度阈值、模板低频覆盖不足、任一标的资料不足或 IPS 必填项缺失时，禁止导出人工交易清单。
- 导出文件必须标注“非订单、税费未计、以券商当日价格和交易单位为准”。

### P0-5：解决当前数据库职责冲突，并收敛为两库

**问题**：当前 `high_dividend.db` 已存在 `universe_definitions`、`screening_runs`、`screening_results`，但新设计又要求事实库只读、筛选写入 `research.db`；再拆分 `research.db` 与 `profile.db` 会造成跨库引用与恢复复杂度。

**必须修订**：

- 事实发布包只保留事实、采集运行、质量检查和发布清单。
- 既有三张筛选表明确为兼容/废弃表，禁止新写入，或在迁移中移除。
- 将规则、策略、运行、IPS、笔记、观察和草案合并到一个 `workbench.db`；第一版只保留“事实发布包 + 工作库”两库。
- 统一 `instruments` 与 `security_master` 的稳定 `instrument_id` 映射，禁止规则层自行拼接两套主表。

### P0-6：补齐行业专用规则与 ETF 产品范围

**问题**：银行、公用事业和普通工商仅被原则性区分；保险、重资本行业和 ETF 产品范围未被规则化。

**必须修订**：

- 银行使用资本充足、不良率/拨备、盈利与派息；不得使用普通工商经营现金流覆盖。
- 公用事业使用经营现金、资本开支、债务期限和监管/电价机制。
- 无行业规则集的标的只能资料不足，不得借用普通工商阈值。
- 首版红利 ETF 仅纳入境内交易所上市、权益红利指数 ETF、产品资料完整的基金；债券、商品、货币、QDII、REITs 等单列或排除。

## 三、P1：MVP 开发前应明确

1. **规则 DSL 与字段目录**：补充阈值、单位、参数类型、`all/any/not`、缺失策略、并列排序、字段/引擎版本与人类可读原因码。
2. **策略与草案状态机**：`draft → reviewed → locked → archived`；锁定版本保存本金、价格、交易单位、费用、现金规则和所有约束检查。
3. **IPS 门槛分层**：浏览研究可采用轻量偏好；导出交易清单必须填写期限、现金需求、是否依赖分红、最大永久损失、单标的/行业/周期/ETF 上限和现金预留。默认值只能是“待确认”，不能暗中预填比例。
4. **估值定位**：首版要么明示“未做估值判断”，要么建立行业适配估值模块；不得把估值写成观察原因却不定义其数据与规则。
5. **技术边界**：Tauri 直接只读事实发布包；复杂策略以受控 Python sidecar 的 JSON stdin/stdout 执行，不开本地 TCP 服务；App、sidecar、`launchd` 共享版本化运行时包。
6. **备份恢复**：发布包天然保留事实历史；`workbench.db` 做 SQLite online backup。恢复必须先校验完整性、manifest 和 schema，在临时位置验证后再原子切换。
7. **ETF 与直接持股重叠**：组合检查至少提示行业、前十大或单一成分股重叠；规模、成交、费用不替代跟踪偏离、折溢价和清盘风险。

## 四、P2：后续增强

- 提供 2–4 个标的的并列比较，降低“追逐最高 TTM 收益率”的倾向；
- 记录人工例外、复核结论与超限理由；
- 分屏展示历史现金分配与历史总回报；
- 设置研究项等待条件模板（下次年报、分红公告、估值变化）；
- 增加旧发布包打开、数据库损坏恢复和工作库恢复的演练；
- 增加可移植的规则/草案/笔记 JSON 导出与离线诊断包。

## 五、审阅分歧与裁决建议

唯一重要分歧是 IPS：UX 审阅建议首次仅收集三项，降低使用门槛；投资审阅要求完整 IPS 才能让系统生成金额和数量。建议同时采纳：

- 浏览候选、加入观察：只需本金、偏好、是否允许周期仓；
- 生成或导出交易清单：必须完成 P1 所列完整 IPS 门槛；
- 缺失 IPS 时系统仅保存“研究草案”，不展示可执行数量或资金分配。

## 六、建议的修订后实施顺序

1. 统一主数据、不可变发布包、全局发布器与覆盖矩阵；
2. PIT 字段目录、行业规则集、ETF 产品分类；
3. 规则引擎与理由输出；
4. `workbench.db`、策略版本、IPS 和草案状态机；
5. Tauri 桌面壳与只读查询；
6. 发布包、草案和工作库的恢复演练后验收。
